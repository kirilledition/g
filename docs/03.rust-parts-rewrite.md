Yes. There are more rewrite opportunities, and a few are high-value. But I would be selective: the best architecture is **not “move everything to Rust.”** The best architecture is:

```text
Rust:
  streaming file formats
  sample/prediction alignment
  BGEN decode/preprocessing
  CPU score-only streaming backend
  output writing/finalization
  manifest/resume/telemetry sinks

Python:
  public API
  CLI/TOML/config normalization
  execution planning
  JAX runtime setup
  high-level orchestration

JAX:
  GPU multi-phenotype kernels
  binary Firth / approximate Firth
  dense linear algebra where batching is large enough
```

The next rewrites I would seriously consider are below.

---

# 1. Biggest opportunity: add a Rust streaming score-only backend

This is the most important “maybe move more to Rust” idea.

Right now the active architecture is roughly:

```text
Rust BGEN decode
    ↓
host genotype chunk matrix
    ↓
Python callback
    ↓
JAX device_put
    ↓
JAX score test
    ↓
device_get
    ↓
Rust writer
```

That is a good GPU architecture when there is enough work per decoded genotype chunk, especially for multi-phenotype scans or Firth-heavy binary runs.

But for **single phenotype score-only linear/binary**, this can be overkill. You pay for:

```text
materializing genotype matrix
host → device transfer
JAX dispatch
device → host transfer
Python callback overhead
```

For single-trait score-only association, the work per genotype byte is low. A Rust streaming backend could compute the score while decoding the BGEN block, without ever materializing or transferring the full genotype chunk.

## Target architecture

For quantitative score-only:

```text
Rust BGEN decode
    ↓
for each variant:
  stream dosage values
  accumulate:
    sum_g
    sum_g2
    dot(g, residual)
    dot(g, whitened_covariates[k])
  compute beta/se/chisq/log10p
    ↓
Rust writer
```

For binary score-only:

```text
Rust BGEN decode
    ↓
for each variant:
  stream dosage values
  accumulate:
    score = dot(g, y - p)
    weighted_g2 = dot(g², W)
    covariate projection terms
  compute beta/se/chisq/log10p
    ↓
Rust writer
```

This avoids:

```text
large genotype matrix allocation
H2D transfer
JAX dispatch
D2H result materialization through Python
```

## When to use it

Add backend selection:

```text
--g-association-backend auto|jax|rust-score
```

Default `auto` could choose:

```text
single phenotype + score-only + CPU or low GPU arithmetic:
  rust-score

multi-phenotype quantitative:
  jax

binary --firth --approx:
  jax

GPU requested and phenotype_count >= threshold:
  jax
```

## Why this is worth exploring

REGENIE is fast because it is a streaming CPU engine. If `g` wants to beat it on single-trait score-only runs, pushing every genotype chunk through GPU may not be the right architecture. A Rust streaming score backend lets you compete in the same streaming regime while still keeping the GPU path for workloads where GPU actually wins.

This is a large rewrite, but it is strategically important.

# 2. Remove or quarantine row-major BGEN decode paths

Your current production paths appear to prefer variant-major delivery. That is the right layout for per-variant association testing.

If pre-release compatibility is not needed, consider making this the rule:

```text
Rust BGEN engine always emits variant-major chunks.
Sample-major is internal/test-only or deleted.
```

Current row-major paths add complexity:

```text
row-major decode
row-major preprocessing
row-major callbacks
sample-major JAX wrappers
variant-major wrappers
transpose fallbacks
```

If the public engine always uses variant-major, you can simplify a lot.

## Recommended direction

Keep only:

```text
run_bgen_variant_major_dosage_buffered_chunks(...)
```

as production.

For Firth paths that still want sample-major genotype matrices, transpose on device inside the JAX path:

```text
variant-major host buffer
    ↓
device_put
    ↓
transpose on device only when Firth path needs it
```

Score-only linear and binary should consume variant-major directly.

## Benefit

```text
less code
fewer tests
fewer layout bugs
more focused SIMD work
fewer memory-layout branches
easier future native score backend
```

I would not delete row-major immediately if tests still depend on it, but I would mark it deprecated/internal and stop adding features to it.

# 3. Move multi-phenotype grouping/planning into Rust or a native planning layer

Current multi-phenotype complete-case mode is useful but semantically different from per-phenotype runs. The better next step is:

```text
group phenotypes by identical aligned sample set and covariate matrix
```

Then run one BGEN pass per group.

## Why this matters

Many phenotype columns will naturally share the same valid sample set and same covariates. You can get multi-phenotype batching without forcing complete-case intersection across all requested phenotypes.

## Suggested architecture

```text
Rust alignment:
  align each phenotype
  produce sample-index fingerprint
  produce covariate-design fingerprint
  group compatible phenotypes

ExecutionPlan:
  groups:
    group_1: phenotypes [BMI, height, weight], same samples/covars
    group_2: phenotypes [LDL, HDL], same samples/covars
    group_3: phenotype [rare_missing_trait], singleton
```

Then the engine does:

```text
for group:
  decode BGEN once
  compute all phenotypes in group
```

## Should this be Rust?

The grouping itself can be Python, but the fingerprints and alignment results should come from Rust because Rust already owns alignment and sample indices.

Best split:

```text
Rust:
  align all phenotypes and return NativePhenotypeGroupPlan

Python:
  convert group plan into ExecutionPlan groups
```

This is a high-value rewrite because it improves GPU utilization without changing statistical semantics.

# 4. Move chunk handles fully into Rust

You already started this with `NativeChunkHandle`, but there is still Python/Rust metadata cycling.

The ideal path is:

```text
Rust BGEN decode creates:
  NativeChunkHandle {
    metadata: Arc<VariantMetadataColumns>
    stats: Arc<ChunkStats>
    chunk_identifier
  }

Python callback receives:
  genotype buffer
  NativeChunkHandle

JAX computes:
  beta/se/chisq/log10p arrays

Python passes:
  NativeChunkHandle + result arrays

Rust writer:
  writes using handle, no metadata clone
```

## Benefit

Avoid repeated copies of:

```text
chromosome strings
variant IDs
alleles
positions
chunk stats vectors
```

At biobank scale, metadata copying is not the top bottleneck, but it is unnecessary architecture noise.

## What to change

Currently, the writer path still has a compatibility function that accepts metadata/stats and clones them into an `Arc`. Replace the public PyO3 writer method with a handle-first method:

```rust
write_regenie2_native_chunk_handle(
    chunk_handle: NativeChunkHandle,
    beta: PyReadonlyArray1<f32>,
    se: PyReadonlyArray1<f32>,
    chisq: PyReadonlyArray1<f32>,
    log10p: PyReadonlyArray1<f32>,
    extra_code: Option<PyReadonlyArray1<i32>>,
)
```

Keep the old metadata-based method only for tests, or remove it pre-release.

# 5. Move strict resume repair into Rust

Current manifest compatibility is much better, but hard-crash resume still deserves a native repair mode.

The Rust writer already embeds chunk commit metadata in Arrow chunk files. That means Rust can implement:

```text
scan chunks directory
open every Arrow file
read chunk commit metadata
validate schema and row counts
rebuild committed_chunks
write repaired manifest
```

## Add command behavior

```bash
g regenie --g-resume --g-resume-mode strict
```

Strict should mean:

```text
do not trust filenames
do not trust manifest alone
open Arrow files
validate chunk metadata
repair manifest if safe
resume only validated chunks
```

## Why Rust

Arrow IPC parsing is already Rust-side. Manifest writing is already Rust-side. Keeping repair native avoids a Python Arrow dependency and keeps output integrity close to the writer.

This is a strong candidate to move fully into Rust.

# 6. Move telemetry sink ownership to Rust

Your current logging setup is good but still split between Python telemetry files and Rust tracing files.

The best end-state is:

```text
Rust owns the telemetry writer queue.
Rust tracing writes into it.
Python emits structured events through a cheap PyO3 call.
One writer owns the file.
```

## Target architecture

```text
_core.start_telemetry_session(config) -> TelemetrySession
_core.emit_python_event(session, event_dict_json)
Rust tracing layer emits native events to same queue
_core.finish_telemetry_session(session)
```

This avoids:

```text
Python opening/closing files per event
Python/Rust writing separate “events” files with confusing ownership
two unrelated queue policies
```

## Keep Python lightweight

Python should only do:

```python
telemetry.event("execution_plan_prepared", phenotype_count=...)
```

No heavy logging library required.

## Why Rust

Rust already has `tracing`, `tracing-appender`, non-blocking writers, and owns the hot native events. Let Rust be the physical telemetry sink.

# 7. Move REGENIE text output to Rust, if you want compatibility output

Right now Parquet/Arrow output is the performance path. That is good.

If you want true REGENIE-compatible `.regenie` text output, write it in Rust as a typed writer. Do not generate it in Python and do not use generic Arrow cell-to-string conversion.

## Target

```rust
finalize_output_run_to_regenie_tsv(...)
```

Typed loops:

```text
CHROM: string
GENPOS: int64
ID: string
ALLELE0/1: string
A1FREQ/INFO/BETA/SE/CHISQ/LOG10P: f32 formatter
N: int32
TEST: ADD
EXTRA: null or TEST_FAIL
```

## Output modes

```text
--g-output-format parquet
--g-output-format arrow
--g-output-format regenie
--g-output-format both
```

Keep default performance output as Parquet unless drop-in REGENIE pipelines become the product priority.

# 8. Move native stats into JAX kernel inputs

This is not “move compute to Rust,” but it uses Rust work to reduce GPU work.

Rust already computes:

```text
dosage_sum
dosage_square_sum
imputed_dosage_square_sum
observation_count
allele counts
zero/nonzero counts
```

The JAX kernels still recompute some things from genotype matrices.

## Linear

Avoid:

```python
jnp.einsum("ij,ij->i", G, G)
```

by passing native `sum_g` and `sum_g2`.

If high-frequency normalization subtracts `2` for variants with mean dosage > 1:

```text
sum((g - c)^2) = sum_g2 - 2c sum_g + n c²
```

So Rust stats can remove a full GPU read/reduction.

## Binary

Use native `dosage_sum` for allele flipping:

```text
flip_mask = dosage_sum > sample_count
```

instead of:

```python
jnp.sum(G, axis=1)
```

This removes a full reduction over the chunk.

## Benefit

This is likely a medium win and low architectural risk.

# 9. Move trusted BGEN validation and SIMD dispatch control deeper into Rust

The trusted fast path should be self-contained:

```text
trusted mode enabled
    ↓
Rust checks validation cache / force validates / assumes validated
    ↓
Rust records validation result in manifest/profile
    ↓
Rust decode path skips redundant per-variant validation where allowed
```

Add native config:

```text
G_BGEN_SIMD=auto|scalar|avx2
```

or a real CLI option:

```text
--g-bgen-simd auto|scalar|avx2
```

Use this for benchmarks and reproducibility.

Do not expose AVX512 as default. If you keep it, make it explicit:

```text
--g-bgen-simd avx512-experimental
```

Given your benchmark result, AVX2 should be the production SIMD target.

# 10. Move sample parsing one step further: direct-fill alignment

`src/sample.rs` is much better now, but it still does this conceptually:

```text
read phenotype records into HashMap
read covariate records into HashMap
loop samples and build aligned rows
for multi-phenotype:
  build per-trait aligned samples
  intersect positions
```

The next rewrite is direct-fill:

```text
build sample_key -> sample row index
allocate phenotype arrays/masks
stream phenotype file once
fill values directly
stream covariate file once
fill values directly
compact complete cases
```

For multi-phenotype:

```text
phenotype_matrix[trait, sample]
phenotype_valid_mask[trait, sample]
covariate_valid_mask[sample]
```

Then derive:

```text
per-phenotype sample sets
complete-case groups
identical-sample-set groups
```

## Benefit

```text
fewer allocations
less string cloning
no per-trait AlignedSampleData construction
easier grouping by sample set
faster large phenotype files
```

This is worth doing, but after the current O(N²) complete-case intersection bug is fixed.

# 11. Move prediction grouping/alignment into the same native planning step

Predictions and phenotypes should share one alignment contract:

```text
sample_key_mode
sample indices
phenotype sample set
prediction sample set
covariate sample set
```

The native layer should be able to say:

```text
these phenotypes can be batched together because:
  same sample_indices
  same covariate matrix
  same prediction sample order
```

Right now Python builds prediction sources after alignment. That is fine, but grouping would be cleaner if Rust returned a single native “run input plan”:

```rust
NativeRunInputPlan {
    groups: Vec<NativePhenotypeGroup>,
    prediction_sources: ...
}
```

This is not urgent, but it is the clean end-state.

# 12. Things I would not move to Rust

## CLI and config normalization

Keep in Python.

The Click/TOML/dataclass layer is much nicer in Python, and it is not a hot path.

## JAX runtime setup

Keep in Python.

JAX is Python-native. Rust should not own JAX platform/cache policy.

## Firth GPU kernels

Do not move to Rust unless you are writing custom CUDA/Pallas/Triton kernels later.

Rust CPU Firth may be useful someday for a CPU backend, but it is not the best next move.

## GPU compute in Rust Burn

I would not move to Burn. It does not solve your main problems:

```text
BGEN streaming
host-device transfer
JAX/XLA fusion
Firth numerical parity
multi-phenotype batching
```

JAX remains the right accelerator layer for now.

## General DataFrame/table processing

Do not add Polars Rust or PyArrow-like abstractions to the core. The current “streaming parser + typed arrays” direction is better.

# Suggested rewrite roadmap

## Phase 1: fix current high-impact issues

Before moving more into Rust, fix these:

```text
1. JIT/fuse binary variant-major score-only path.
2. Remove multi-binary T × V × S intermediate.
3. Fix O(T × N²) complete-case intersection.
4. Fail by default on null logistic non-convergence.
5. Output NaN for invalid binary score rows.
```

These are correctness/performance blockers.

## Phase 2: Rust-native infrastructure rewrites

```text
6. Add strict resume scan/repair in Rust.
7. Move telemetry physical sink to Rust.
8. Replace writer metadata/stat cloning with NativeChunkHandle end-to-end.
9. Add G_BGEN_SIMD / --g-bgen-simd override.
10. Direct-fill sample/phenotype/covariate alignment.
```

## Phase 3: Rust score-only backend prototype

Build a prototype behind an explicit flag:

```bash
g regenie ... --g-association-backend rust-score
```

Support only:

```text
quantitative score-only
binary score-only
single phenotype first
trusted variant-major BGEN first
```

Then benchmark against:

```text
REGENIE CPU
g JAX CPU
g JAX GPU
```

If it wins or is close, expand it.

## Phase 4: smarter multi-phenotype planning

```text
group phenotypes by identical sample/covariate/prediction alignment
one BGEN pass per group
JAX GPU for large groups
Rust-score backend for singleton/low-arithmetic groups
```

This gives you the best of both worlds.

# My strongest recommendation

The most promising rewrite is not “more of the current Python callback into Rust.” It is this:

```text
Add a Rust streaming score-only backend.
```

That gives you a second execution mode optimized for the workload where GPU is weakest:

```text
single-trait or low-trait score-only association
```

Then keep the JAX/GPU backend for the workload where GPU is strongest:

```text
multi-phenotype batched scans
binary Firth / approximate Firth
large dense matrix operations
```

The final architecture should be a planner that chooses between:

```text
rust-score:
  low arithmetic intensity, score-only, streaming-friendly

jax-gpu:
  high arithmetic intensity, multi-phenotype, Firth-heavy

jax-cpu:
  fallback/debug/reference
```

That is probably the path to making `g` faster than REGENIE in the cases where GPU helps, while not forcing GPU overhead onto cases where a Rust streaming CPU engine is the better tool.
