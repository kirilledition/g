Yes. I would set this up, but I would **not** let many parallel agents all merge and push `main` independently without a lock or an integration queue. That is the one dangerous part of your desired workflow.

The safe design is:

```text
parallel workers:
  pick independent tasks
  create task branch + worktree
  implement
  test
  update plan file with result/discoveries
  push task branch

serial integrator:
  review branch
  merge to main
  run checks
  push main
  remove worktree
  mark task merged
```

If you insist that each worker can merge to `main` itself, add a **global integration lock** so only one agent can touch `main` at a time. Git worktrees are excellent for parallel implementation, but `main` is still one mutable branch.

Codex supports the pieces you want: `codex exec` is intended for non-interactive automation, and the docs explicitly say it can be used from scripts. ([OpenAI Developers][1]) `/goal` is available in interactive CLI threads; it keeps a goal attached to the active thread, but objectives are capped at 4,000 characters, so longer process instructions should live in a file that the goal points to. ([OpenAI Developers][2]) Codex subagents can run specialized agents in parallel and collect results, but Codex only spawns them when explicitly asked, and they inherit the parent sandbox/approval policy. ([OpenAI Developers][3])

# 2. Persistent `/goal` file

Create:

```md

You are operating a task farm for this repository.

Primary objective:
Complete every ready task in `docs/code-review-plan.md` safely and update the plan with the outcome.

Hard invariants:
1. Never edit the main checkout for task implementation.
2. Every implementation task gets its own branch and git worktree.

   - the task branch is reviewed or explicitly marked `review skipped`,
   - required tests/checks were attempted,
   - the integration lock is held,
   - main was updated with `git pull --ff-only`,
   - the merge result passes checks.
7. Only one agent may merge/push main at a time.
8. After a successful merge and push, remove the task worktree and mark the task `merged`.
9. If a conflict or test failure cannot be resolved safely, abort the merge, mark the task `blocked`, keep the branch/worktree, and write the blocker in the plan.
10. Do not delete evidence: logs, benchmark results, or failed hypothesis notes are useful.

Recommended workflow:
1. Read `docs/code-review-plan.md`.
2. Pick one `ready` task with no unmet dependencies.
3. Mark it `running` in the plan and commit that status update if working in a task branch.
4. Create a branch and worktree matching the task block.
5. Implement the task narrowly.
6. Run required validation.
7. Update the task block with:
   - summary
   - files changed
   - tests run
   - benchmark results, if any
   - discoveries
   - remaining risks
8. Commit changes.
9. Review or request review.
10. Integrate serially through main.
11. Push main.
12. Remove the worktree.
```

Then in an interactive Codex session:

```text
/goal Follow docs/codex-goal.md. Continue until all ready tasks in docs/code-review-plan.md are merged or explicitly blocked.
```

Use `/goal` as the persistent objective, not as the whole instruction payload.

# 4. The central safety issue: merging main

Parallel implementation is great. Parallel `main` merges are not.

Git itself enforces that a branch can only be checked out in one worktree at a time, and Codex’s worktree docs explain that this rule exists to avoid ambiguity and race conditions around a mutable branch reference. ([OpenAI Developers][4])

So use one of these two policies.

## Recommended policy: workers do not merge main

```text
parallel workers:
  branch + worktree + commit + push task branch

serial integrator:
  merge reviewed branches to main one by one
```

This is best.

## Aggressive policy: workers may merge main, but only with lock

Add a lock:

```text
.codex-task-worktrees/integration.lock
```

Use `flock` on Linux/macOS:

```bash
flock .codex-task-worktrees/integration.lock -c 'scripts/codex-integrate-task.sh T001'
```

Every agent must use the lock before:

```text
git checkout/switch main
git pull
git merge
git push origin main
git worktree remove
```

Without that lock, two successful workers can race and one can push over the other’s assumptions.

# 5. Script skeleton

Purpose:

## `scripts/codex-create-worktree.sh`

```bash
#!/usr/bin/env bash
set -euo pipefail

TASK_ID="${1:?task id required}"
BRANCH="${2:?branch required}"
WORKTREE="${3:?worktree path required}"
BASE_BRANCH="${BASE_BRANCH:-main}"

git fetch origin "$BASE_BRANCH"
git switch "$BASE_BRANCH"
git pull --ff-only origin "$BASE_BRANCH"

mkdir -p "$(dirname "$WORKTREE")"

if git show-ref --verify --quiet "refs/heads/$BRANCH"; then
  git worktree add "$WORKTREE" "$BRANCH"
else
  git worktree add -b "$BRANCH" "$WORKTREE" "$BASE_BRANCH"
fi

echo "$WORKTREE"
```

## `scripts/codex-run-worker.sh`

```bash
#!/usr/bin/env bash
set -euo pipefail

TASK_ID="${1:?task id required}"
WORKTREE="${2:?worktree required}"
LOG_DIR=".codex-task-worktrees/runs/$TASK_ID"
PROMPT="$LOG_DIR/worker-prompt.md"

mkdir -p "$LOG_DIR"

cat > "$PROMPT" <<EOF
You are task_worker for task $TASK_ID.

Read:
- docs/codex-goal.md
- docs/code-review-plan.md
- AGENTS.md if present
- docs/STYLEGUIDE.md if present

Work only in this worktree:
$WORKTREE

Implement exactly task $TASK_ID.
Update that task's Agent log in docs/code-review-plan.md.
Commit your changes.
Leave the worktree clean.
EOF

codex --cd "$WORKTREE" exec --json -o "$LOG_DIR/final.json" "$(cat "$PROMPT")" \
  > "$LOG_DIR/stdout.jsonl" \
  2> "$LOG_DIR/stderr.log"
```

The docs say `codex exec` runs non-interactively and pipes final plan/results back to stdout, so this is the correct automation primitive. ([OpenAI Developers][1])

## `scripts/codex-review-task.sh`

#!/usr/bin/env bash

# 7. Non-interactive task farm workflow

For more reliable repeatability than an interactive `/goal`, use `codex exec` plus your scripts.

Example driver:

```bash
#!/usr/bin/env bash
set -euo pipefail

MAX_JOBS="${MAX_JOBS:-4}"

mkdir -p .codex-task-worktrees/runs .codex-task-worktrees/reviews

# Claim/create/run workers in parallel.
for i in $(seq 1 "$MAX_JOBS"); do
  (
    TASK_JSON="$(flock .codex-task-worktrees/claim.lock python scripts/codex-claim-task.py)"
    TASK_ID="$(jq -r .id <<< "$TASK_JSON")"
    BRANCH="$(jq -r .branch <<< "$TASK_JSON")"
    WORKTREE="$(jq -r .worktree <<< "$TASK_JSON")"

    scripts/codex-create-worktree.sh "$TASK_ID" "$BRANCH" "$WORKTREE"
    scripts/codex-run-worker.sh "$TASK_ID" "$WORKTREE"
    scripts/codex-review-task.sh "$TASK_ID" "$WORKTREE"

    # Either stop here and let a human/integrator merge,
    # or integrate under a global lock:
    flock .codex-task-worktrees/integration.lock \
      scripts/codex-integrate-task.sh "$TASK_ID" "$BRANCH" "$WORKTREE"
  ) &
done

wait
```

This is more predictable than relying on the coordinator agent to remember every shell invariant.

# 9. Recommended task lifecycle states

Use these states in `docs/code-review-plan.md` and/or JSON state:

```text
ready
claimed
running
implemented
reviewing
needs_changes
reviewed
integrating
merged

abandoned
```

Meanings:

```text
ready:
  available to claim

claimed:
  task reserved, worktree may be in creation

running:
  worker is editing

implemented:
  branch has committed changes and clean worktree

reviewing:
  reviewer is active

needs_changes:
  reviewer found fixable issues

reviewed:
  accepted for integration

integrating:
  integration lock held or waiting

merged:
  merged and pushed to main; worktree removed

blocked:
  cannot proceed safely

abandoned:
  hypothesis was tried and did not work; evidence recorded
```

Do not delete abandoned tasks. They are valuable performance history.

# 12. Safety guardrails I would enforce

## Never run all workers with unrestricted full access by default

Use normal workspace write for workers. Use read-only for reviewers. Use integration scripts for branch operations.

## Protect `main`

Only integration code may touch `main`. Use:

```bash
flock .codex-task-worktrees/integration.lock ...
```

## Require clean worktrees

Before integration:

```bash
git -C "$WORKTREE" status --short
```

must be empty.

## Require branch is ahead

Before review/integration:

```bash
git -C "$WORKTREE" log --oneline main..HEAD
```

must show commits.

## Push task branches first

Even if integration is local:

```bash
git push -u origin "$BRANCH"
```

This gives you recovery if the local worktree is removed incorrectly.

## Do not remove failed worktrees

Only cleanup after:

```text
main push succeeded
task status was marked merged
```

Blocked/needs-changes worktrees stay for inspection.

# 13. Practical operating modes

## Mode A — safest daily mode

```text
workers:
  parallel implementation branches

review:
  parallel read-only subagents

integration:
  one serial integrator
```

Use this most of the time.

## Mode B — fully autonomous but locked

```text
worker:
  implements
  reviews itself or calls reviewer
  waits for integration lock
  merges/pushes/removes worktree
```

This is what you asked for, but only safe with a lock and strong scripts.

## Mode C — human-gated

```text
workers:
  implement and push branches

human:
  chooses merge order

integrator:
  merges chosen branch
```

Use this for P0 statistical/math tasks.

# Final recommendation

Set it up like this:

```text
1. Put long instructions in docs/codex-goal.md.
2. Track tasks in docs/code-review-plan.md.
3. Configure subagent limits in .codex/config.toml.
4. Add task_worker, task_reviewer, and task_integrator custom agents.
5. Use /goal to bind the operating contract to the coordinator thread.
6. Use subagents for parallel implementation/review.
7. Use Git worktrees for actual isolation.
8. Use a global integration lock for anything that touches main.
9. Require every task to update the plan with results, failed hypotheses, tests, and risks.
```

The only part I would push back on is “every parallel agent merges to main independently.” The reliable version is:

```text
parallel workers, serial integration
```

or:

```text
parallel workers, locked self-integration
```

Without that lock, the system will eventually race on `main`.
