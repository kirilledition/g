# Executive assessment

This version is a meaningful improvement over the prior state. The architecture is moving in the right direction: config and execution planning are cleaner, compute modules are split, telemetry exists, Rust sample parsing is streaming, and the trusted BGEN fast path has started to use integer/SIMD ideas.

However, there are still several serious problems. The biggest ones are:

```text
1. Binary variant-major compute appears to have lost top-level JIT fusion.
2. Multi-binary score computation materializes or risks materializing a huge T × V × S tensor.
3. Multi-phenotype complete-case alignment has an O(T × N²) intersection bug.
4. Binary null logistic non-convergence is still not fail-fast.
5. Invalid binary score rows can output CHISQ=0 / LOG10P≈0 instead of NaN.
6. Resume after hard crash still seems weaker than the manifest design implies.
7. Several GPU reductions and host-device transfers can be avoided with native stats.
```

If this were heading toward a first internal release, I would fix items 1–5 before trusting performance or statistics.

# P1 performance issues


## 8. Linear kernels reread genotype data for sum of squares that Rust already knows

In `src/g/compute/regenie2_linear/score.py:22-41`, the kernel normalizes genotypes and computes:

```python
genotype_sum_squares_compute = jnp.einsum(
    "ij,ij->i",
    normalized_genotype_matrix_by_variant,
    normalized_genotype_matrix_by_variant,
)
```

But Rust chunk stats already include genotype sums and square sums. The output writer tests show `ChunkStats` has:

```rust
dosage_sum
dosage_square_sum
imputed_dosage_square_sum
```

The linear kernel needs the normalized sum of squares. Since normalization subtracts either `0` or `2` per variant:

```text
sum((g - c)^2) = sum(g²) - 2c·sum(g) + n·c²
```

where `c ∈ {0, 2}`.

### Fix

Pass native per-variant `dosage_sum` and `imputed_dosage_square_sum` to the linear JAX kernel.

Then compute:

```python
genotype_mean = dosage_sum / sample_count
offset = jnp.where(genotype_mean > 1.0, 2.0, 0.0)
normalized_sum_squares = sum_g2 - 2.0 * offset * sum_g + sample_count * offset * offset
```

This avoids a full GPU pass over the genotype matrix.

For single-trait quantitative REGENIE, that matters because the kernel is memory-bandwidth-bound.

## 9. Binary genotype flipping also duplicates native work

In `src/g/compute/common/genotype.py:89-95`:

```python
allele_count = jnp.sum(genotype_matrix_by_variant, axis=1)
flip_mask = allele_count > sample_count
flipped_genotype_matrix_by_variant = jnp.where(...)
```

Rust already computes dosage sums. You can pass native `dosage_sum` to the binary score kernel and compute the flip mask without reducing `G` on GPU.

You still need the flipped genotype values for score/correction, so this does not remove all work. But it removes one full reduction over the chunk.

### Recommendation

Add an optional `dosage_sum` argument to binary score kernels:

```python
def compute_binary_score_test_chunk_variant_major(..., dosage_sum: jax.Array | None = None):
    ...
```

Use native sum when available. Fall back to `jnp.sum` for tests or non-native callers.

## 10. Multi-binary Firth loops over traits in Python

In `src/g/compute/regenie2_binary/api.py:112-145`, multi-binary Firth does:

```python
for trait_index in range(trait_count):
    compute_one_trait(...)
```

and then stacks results.

This is probably acceptable for early Firth support because exact multi-trait Firth batching is hard. But it means multi-binary `--firth --approx` is not really a fully batched GPU workload. It is closer to sequential trait processing sharing a genotype transfer.

### Recommendation

Document this internally and benchmark separately:

```text
multi-binary score-only:
  should be true batched GPU compute

multi-binary approximate Firth:
  currently per-trait correction loop after shared transfer
```

Do not claim full multi-trait binary Firth acceleration until this is improved.

## 11. The current AVX2 path still scalarizes statistics inside the vector loop

`src/genotype/bgen/simd.rs:293-337` vectorizes raw dosage decoding and f32 storage, but then it stores the vector back to a stack array and loops over lanes:

```rust
let mut raw_dosage_chunk = [0_i32; AVX2_SAMPLE_COUNT];
_mm256_storeu_si256(raw_dosage_chunk.as_mut_ptr().cast::<__m256i>(), raw_dosage_integers);

for raw_dosage_integer in raw_dosage_chunk {
    raw_integer_summary.record_raw_dosage_integer(raw_dosage_integer);
}
```

That is correct, but it leaves performance on the table.

### Fix

Keep the current version as a correctness baseline, then implement vector accumulation:

```text
raw_sum: i32/i64 vector accumulators
raw_square_sum: i32/i64 with periodic horizontal reduction
zero/nonzero counts: comparison masks + popcount
hom_ref/het/hom_alt counts: comparison masks + popcount
```

Periodically reduce to scalar `u64/i64` to avoid overflow.

Also add a runtime override:

```text
G_BGEN_SIMD=auto|scalar|avx2
```

Right now dispatch is automatic AVX2 if available (`simd.rs:110-125`), which makes benchmarking scalar vs AVX2 annoying.

## 12. SIMD test allows impossible negative dosages

In `src/genotype/bgen/simd.rs:537-538`:

```rust
assert!(output.iter().all(|dosage_value| (-1.0..=2.0).contains(dosage_value)));
```

For valid unphased 8-bit BGEN probabilities where `p0 + p1 <= 255`, dosage should be:

```text
0 <= dosage <= 2
```

The test should not allow `-1.0`.

### Fix

Tighten this to:

```rust
assert!(output.iter().all(|dosage_value| (0.0..=2.0).contains(dosage_value)));
```

If the test generator can create invalid probability pairs, fix the generator, not the assertion.

# P1 correctness / numerical concerns

## 13. `jax-enable-x64` is misleading

The config default has:

```toml
jax-enable-x64 = true
```

and `GComputeConfig` exposes `jax_enable_x64`.

But much of the compute code explicitly casts to float32:

```python
# linear state
covariate_matrix_compute = jnp.asarray(covariate_matrix, dtype=jnp.float32)
phenotype_matrix_compute = jnp.asarray(phenotype_matrix, dtype=jnp.float32)

# binary score
raw_genotype_matrix_by_variant = jnp.asarray(genotype_matrix_by_variant, dtype=jnp.float32)

# p-values
safe_chi_squared = jnp.maximum(jnp.asarray(chi_squared, dtype=jnp.float32), 0.0)
```

Relevant files:

```text
src/g/compute/regenie2_linear/state.py
src/g/compute/regenie2_binary/score.py
src/g/compute/common/pvalue.py
```

This is not necessarily wrong. Float32 may be the desired fast path. But the config suggests broader x64 behavior than the kernels actually provide.

### Fix

Make the policy explicit:

```text
jax-enable-x64:
  enables JAX's ability to create x64 arrays, mainly for Firth internals

score-dtype:
  float32 | float64

firth-dtype:
  float64
```

Or remove `jax-enable-x64` from the user-facing tuning surface and keep it internal.

## 14. P-value conversion always downgrades to float32

In `src/g/compute/common/pvalue.py:24`:

```python
safe_chi_squared = jnp.maximum(jnp.asarray(chi_squared, dtype=jnp.float32), 0.0)
```

If a Firth path produces float64 chi-square values, this discards precision before tail conversion.

### Fix

Preserve float64 when present:

```python
chi_squared_array = jnp.asarray(chi_squared)
dtype = jnp.result_type(chi_squared_array, jnp.float32)
safe_chi_squared = jnp.maximum(chi_squared_array.astype(dtype), jnp.asarray(0.0, dtype=dtype))
```

Or explicitly provide:

```python
chi_squared_to_log10_p_value_float32
chi_squared_to_log10_p_value_float64
```

For extreme GWAS tails, this deserves parity testing.

## 15. Linear LOCO/covariate formula still needs parity tests

The linear state residualizes phenotype against covariates first and subtracts LOCO predictions later. The API doc says:

```text
adjusted_residual = phenotype_residual - loco_predictions
```

That may match how REGENIE’s Step 1 predictions are intended to be used, but the subtle alternative is:

```text
residualize(y - pred)
```

These differ if LOCO predictions are not covariate-orthogonal.

### Fix

Add a tiny parity fixture where covariates and LOCO predictions are correlated. Compare against REGENIE. Lock the formula down before optimizing linear further.

# P2 memory allocation / host-device transfer issues

## 16. Python telemetry opens and closes the JSONL file for every event

In `src/g/engine/telemetry.py:131-138`:

```python
with self.lock:
    path.parent.mkdir(parents=True, exist_ok=True)
    with path.open("a", encoding="utf-8") as output_file:
        output_file.write(...)
```

This is fine for progress events and low-volume lifecycle logging. It is not fine if you start logging per-chunk debug or trace events through this path.

### Fix

Keep this for `progress` mode, but add a buffered queue writer for `profile` and `trace` modes.

At minimum:

```text
- create directories once
- open files once per telemetry session
- flush on close
- optionally use a bounded queue
```

---

## 17. Logging/telemetry is still split in a confusing way

Python telemetry writes `events.jsonl` and `progress.jsonl`. Rust tracing writes to `log_file` or `trace_file` depending on config.

By default, `diagnostics.log_file` is `None`, while telemetry resolves `events.jsonl` to `<out>.g/logs/events.jsonl`. That means:

```text
events.jsonl = Python telemetry only
Rust JSON tracing = absent unless log_file/trace_file is configured
```

This may be intentional, but the naming suggests a unified event stream.

### Recommendation

Pick one of these designs:

```text
Option A:
  python.events.jsonl
  rust.events.jsonl
  progress.jsonl

Option B:
  events.jsonl is Python lifecycle only
  trace.jsonl is Rust trace only
```

Do not have Python and Rust independently append to the same file unless there is one shared writer.

## 18. Output writer still copies result arrays and clones metadata

In `src/output/session.rs:340-379`, `write_regenie2_native_chunk(...)` creates:

```rust
NativeChunkHandle::new(Arc::new(metadata.clone()), Arc::new(chunk_stats.clone()), ...)
```

and then copies result arrays:

```rust
beta: beta.to_vec(),
se: standard_error.to_vec(),
chisq: chi_squared.to_vec(),
log10p: log10_p_value.to_vec(),
extra_code: extra_code.map(<[i32]>::to_vec),
```

This is not a correctness bug. But at scale it is visible CPU memory traffic.

### Better architecture

The Rust BGEN engine already owns metadata and stats before Python/JAX compute. Long-term, pass a Rust-owned `NativeChunkHandle` through the Python callback:

```text
Rust BGEN decode
    → Python receives genotype buffer + NativeChunkHandle
    → JAX computes numeric arrays
    → Python passes NativeChunkHandle + numeric arrays to writer
```

That avoids metadata/stats cloning through Python.

For result arrays, consider accepting ownership of contiguous NumPy buffers where possible.

## 19. Result arrays are downcast to float32 before writing

`write_regenie2_native_chunk_with_optional_timing(...)` materializes results with `jax.device_get`, then calls:

```python
np.asarray(array, dtype=np.float32)
```

This is consistent with the Arrow schema, but it means any float64 Firth internal results are downcast before output.

If you want REGENIE-compatible text-style output, float32 may be acceptable. If you want high-precision scientific output, this should be configurable or at least documented.

# P2 architecture issues

## 20. Multi-phenotype batching is semantically honest but performance-limited

The current modes are:

```text
per-phenotype
complete-case
```

Default is per-phenotype. Complete-case is explicitly opt-in because it changes sample inclusion semantics. That is correct.

But from a performance perspective, this means common multi-phenotype runs may still decode BGEN repeatedly.

### Better next architecture

Add grouping by identical sample/covariate alignment:

```text
1. Align each phenotype independently.
2. Compute fingerprint of sample_indices + covariate matrix.
3. Group phenotypes with identical fingerprints.
4. Run one BGEN pass per group.
5. Use complete-case only when the user explicitly requests that semantic change.
```

This preserves per-phenotype semantics while still batching many real-world traits.

---

## 21. Rust sample parser is streaming, but still allocates more than necessary

The current Rust sample parser is much better than before, but it still builds maps of owned `SampleKey -> RawPhenotypeRecord` and `SampleKey -> RawCovariateRecord`, then loops BGEN samples later.

For huge phenotype/covariate tables and many phenotypes, the fastest design is:

```text
build sample_key → row_index map once
preallocate phenotype/covariate arrays and masks
stream phenotype table directly into arrays
stream covariate table directly into arrays
compact complete cases
```

For multi-phenotype, this avoids building per-trait `AlignedSampleData` and then intersecting them.

This is not urgent compared with the O(N²) bug, but it is the next cleanup.

---

## 22. Oxford `.sample` parsing may mishandle tabs/mixed whitespace

`open_sample_file_reader(...)` uses the CSV reader with a single space delimiter. Then `space_delimited_record_to_strings(...)` filters empty fields.

If `.sample` files contain tabs or arbitrary mixed whitespace, this may not split correctly.

### Fix

For Oxford `.sample`, a simple line reader with:

```rust
line.split_whitespace()
```

may be more robust than using CSV with `delimiter(b' ')`.

For phenotype/covariate TSV, tab-only is fine if documented.

## 23. `scan_committed_chunk_identifiers` trusts single-chunk filenames

In `src/output/resume.rs:27-31`, if a file name looks like a single-chunk file, the scan inserts the identifier without opening the Arrow file:

```rust
if let Some((first_chunk_identifier, None)) = parse_chunk_file_name(&chunk_file_path) {
    committed_identifiers.insert(first_chunk_identifier);
    continue;
}
```

This helper may not be used for strict resume, but it is risky as a general committed-chunk scanner.

### Fix

For any “strict” or “repair” mode, always open Arrow files and validate schema metadata. Fast mode can trust manifest only. Filename-only inference should be clearly named as fast/unsafe.

## 24. Hard-crash resume still seems weaker than graceful resume

The writer records chunk commits in memory and writes them to the manifest in `finish()` / `finish_interrupted()`:

```rust
# src/output/session.rs
let chunk_commits = self.take_worker_commits()?;
manifest::record_run_manifest_chunk_commits(...)
```

Arrow files are written earlier using temp-file-then-rename in `src/output/writer.rs`.

If the process is killed after Arrow rename but before `finish()` records manifest commits, the chunk file exists but the manifest may not list it. Current `initialize_output_run()` resumes from manifest commits. I did not see a scan-and-repair step in Python output initialization.

### Fix

Add one of:

```text
A. append-only commits.jsonl written after every Arrow rename
B. strict resume repair: scan Arrow metadata, update manifest, then resume
C. fast resume = manifest only; strict resume = manifest + Arrow scan
```

Given Arrow chunk metadata already contains commit records, option B is very natural.

# Recommended implementation plan

## Sprint 1: correctness and severe performance regressions

1. JIT the binary variant-major score-only path.
2. Fix multi-binary score to avoid `traits × variants × samples` materialization.
3. Fix multi-phenotype complete-case alignment from `Vec::contains` to `HashMap::contains_key`.
4. Make binary null logistic non-convergence fail by default.
5. Output NaN for invalid binary score statistics, not `CHISQ=0 / LOG10P=0`.

## Sprint 2: profiling-grade cleanup

6. Add timing for Firth candidate-count host sync.
7. Avoid sparse Firth mask H2D transfer in score-only sample-major paths.
8. Make telemetry file writing buffered for profile/trace.
9. Clarify Python/Rust telemetry stream ownership.
10. Add `G_BGEN_SIMD=auto|scalar|avx2`.

## Sprint 3: native/JAX data movement

11. Pass native `dosage_sum` / `imputed_dosage_square_sum` into linear kernels.
12. Use native `dosage_sum` for binary genotype flip masks.
13. Reduce Rust writer metadata/result copying with `NativeChunkHandle`.
14. Add strict resume scan-and-repair.

## Sprint 4: scientific parity

15. Add REGENIE parity fixture for linear LOCO/covariate correlation.
16. Add binary score-only parity fixtures.
17. Add approximate Firth parity fixtures across toy, medium, and representative full-chromosome data.
18. Add tests for null logistic non-convergence policy.

# Bottom line

The codebase is improving fast, but I would not spend time on cosmetic refactors right now. The next work should be targeted:

```text
1. restore JIT fusion for binary variant-major compute
2. remove the giant multi-binary intermediate
3. fix O(N²) multi-phenotype alignment
4. fail on null logistic non-convergence
5. make invalid binary statistics actually invalid
```

After those are fixed, the app will be in a much stronger state for meaningful benchmarking. Right now, performance numbers could be misleading because at least two major paths are likely dominated by avoidable JAX dispatch/memory behavior rather than the intended Rust/JAX architecture.
